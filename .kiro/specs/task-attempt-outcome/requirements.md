# Requirements: task-attempt-outcome

## Introduction

agent-router is an **execution and observation primitive**: it runs agent sessions and reports what happened. This feature adds a first-class **task / attempt / outcome** model on top of the existing session machinery so that an orchestrator layer above the daemon can submit work, observe structured progress, and interpret results — without parsing free-text agent output.

The guiding design principle: quality judgment, retry policy, scheduling, and outcome interpretation belong in the orchestrator layer, **not** in agent-router. The daemon's job is to execute a task as one or more attempts, record a structured outcome for each attempt, and emit a monotonic, replayable event stream. The completeness test for this feature is: **the web UI should be able to consume only the public `/v1/` API.**

Scope boundaries (explicitly **out of scope** for this feature):

- Quality / verification gate (orchestrator layer)
- Per-repo memory
- Global scheduler
- Land-rate ledger
- Tier 2 PR/CI events (`pr.opened`, `pr.checks_completed`, `pr.closed`)
- Multi-agent orchestration

This spec covers three new SQLite tables (`tasks`, `attempts`, `task_events`), a versioned `/v1/` REST + SSE API, a closed outcome/reason-code contract, an agent outcome-reporting channel, restart (crash-recovery) semantics, two-phase transcript retention, per-repo concurrency with a circuit breaker, and a ROADMAP.md intake adapter.

### Terminology

- **Task** — a unit of work submitted to the daemon: a repo, a prompt (`spec`), and budget/metadata. Identified by a ULID.
- **Attempt** — one execution of a task by an agent session. A task may have multiple attempts (retries). Identified by a ULID; numbered 1-based per task.
- **Outcome** — the structured, closed-enum result of an attempt.
- **Event** — an append-only, monotonically sequenced record in `task_events`, exposed via SSE with replay.
- **Orchestrator** — the external caller above agent-router that submits tasks and decides retry/quality policy.

### Conventions (inherited from existing codebase)

- Timestamps are stored as **unix milliseconds** (INTEGER) in SQLite and serialized as **ISO 8601** strings in JSON API responses.
- Every `/v1/` JSON response body includes `"v": 1`.
- `/v1/` endpoints authenticate with the same bearer token / trusted-proxy mechanism as the existing control-plane API (`createAuthMiddleware`).
- Error responses use the existing envelope shape: `{ "error": { "code": string, "message": string, "details"?: unknown } }`.
- State transitions and the events they produce are written in the **same SQLite transaction**.

## Requirements

### Requirement 1: Task submission and idempotency

**User Story:** As an orchestrator, I want to submit a task with an idempotency key, so that retrying a submission never creates a duplicate task.

#### Acceptance Criteria

1. WHEN a client sends `POST /v1/tasks` with a valid body THEN the daemon SHALL create a `tasks` row with a ULID `id`, persist all supplied fields, set `state = 'queued'`, set `created_at` and `updated_at` to the current unix-ms time, and return `201` with the created task and `"v": 1`.
2. WHEN a `POST /v1/tasks` body omits `external_id` THEN the daemon SHALL create a new task with `external_id = NULL`.
3. WHEN a `POST /v1/tasks` body includes an `external_id` that already exists in `tasks` THEN the daemon SHALL NOT create a new task and SHALL return `200` with the existing task record (idempotent submission).
4. WHEN two submissions with the same `external_id` arrive concurrently THEN the daemon SHALL guarantee that exactly one `tasks` row exists for that `external_id` (enforced by a UNIQUE constraint plus a single transaction).
5. IF the request body is not a JSON object, is missing a required field (`repo`, `title`, `spec`), or contains a field that fails validation THEN the daemon SHALL return `400` with `error.code = 'invalid_body'` and SHALL NOT create a task.
6. IF `repo` does not match a configured repo (`owner/name`) THEN the daemon SHALL return `400` with `error.code = 'invalid_repo'`.
7. WHEN `agent` is omitted THEN the daemon SHALL default it to `'kiro'`; IF `agent` is present AND is not one of `'kiro' | 'claude'` THEN the daemon SHALL return `400` with `error.code = 'invalid_agent'`.
8. WHEN `source` is omitted on an API submission THEN the daemon SHALL default `source` to `'api'`.
9. WHEN `base_ref` is omitted or null THEN the daemon SHALL treat the task as working from the repo's default branch.
10. IF `budget` is present THEN the daemon SHALL validate it as a JSON object whose known fields (`max_wall_s`, `max_tokens`, `max_turns`, `heartbeat_interval_s`, `allow_resume`) have the correct types, rejecting invalid budgets with `400` and `error.code = 'invalid_budget'`.
11. WHEN `metadata` is present THEN the daemon SHALL persist it verbatim and SHALL echo it unchanged on every event emitted for the task.
12. WHEN a task is created THEN the daemon SHALL emit a `task.queued` event (type `task.queued`) in the same transaction as the `tasks` insert.

### Requirement 2: Task retrieval and listing

**User Story:** As an orchestrator (or UI), I want to read a task and its latest attempt, and list tasks filtered by repo and state, so that I can render current status without parsing logs.

#### Acceptance Criteria

1. WHEN a client sends `GET /v1/tasks/:id` for an existing task THEN the daemon SHALL return `200` with the task fields plus a summary of the latest attempt (highest `attempt_no`), or `null` when no attempt exists, and `"v": 1`.
2. IF the task id does not exist THEN the daemon SHALL return `404` with `error.code = 'not_found'`.
3. WHEN a client sends `GET /v1/tasks` THEN the daemon SHALL return `200` with an array of tasks and `"v": 1`.
4. WHEN `GET /v1/tasks` includes `?repo=owner/name` THEN the daemon SHALL return only tasks for that repo.
5. WHEN `GET /v1/tasks` includes `?state=<state>` THEN the daemon SHALL return only tasks in that state; IF `state` is not a valid task state THEN the daemon SHALL return `400` with `error.code = 'invalid_param'`.
6. WHEN both `repo` and `state` are supplied THEN the daemon SHALL apply both filters (logical AND).
7. WHEN timestamps are serialized in any `/v1/` response THEN the daemon SHALL render them as ISO 8601 strings (not raw unix-ms integers).

### Requirement 3: Task state machine

**User Story:** As an orchestrator, I want tasks to move through a well-defined state machine, so that I can reason about what the daemon will do next.

#### Acceptance Criteria

1. The daemon SHALL constrain `tasks.state` to the closed union: `queued | running | succeeded | failed | blocked | cancelled`.
2. WHEN the scheduler claims a `queued` task and starts an attempt for it THEN the daemon SHALL transition the task to `running`. A retry (Requirement 5.1) first moves a `failed`/`blocked` task back to `queued`; it transitions to `running` only when the scheduler subsequently claims it and creates the attempt row.
3. WHEN an attempt ends with outcome `succeeded` THEN the daemon SHALL transition the task to `succeeded`.
4. WHEN an attempt ends with outcome `failed`, `timed_out`, `budget_exceeded`, or `interrupted` THEN the daemon SHALL transition the task to `failed`. For `interrupted` (crash-recovery or lease expiry) the task's `reason_code` is `interrupted`; the daemon SHALL NOT automatically re-queue it (Requirement 13.9 / Requirement 5.3) — an interruption is infrastructural, but automatic re-queueing would create a crash loop for a poison-pill task and would contradict the "no automatic retry" rule. The orchestrator or operator retries explicitly via `POST /v1/tasks/:id/attempts` (Requirement 5.1), or cancels via Requirement 5. In all cases the attempt row itself remains `ended` with its recorded outcome. **The single exception (HIGH-5)** is the bounded `allow_resume = true` restart-resume path of Requirement 13.6: there, an `interrupted` attempt moves its task to `queued` (with a `task.requeued`(`reason='interrupted'`) event) so the scheduler can start exactly one resume attempt; this cannot crash-loop because `resume_session_id` is cleared after one use (Requirement 13.6, HIGH-5(b)), after which a further interruption falls back to `failed`.
5. WHEN an attempt ends with outcome `blocked` THEN the daemon SHALL transition the task to `blocked`.
6. WHEN an attempt ends with outcome `cancelled` THEN the daemon SHALL transition the task to `cancelled`.
7. WHEN the task state changes THEN the daemon SHALL update `tasks.updated_at` to the current unix-ms time in the same transaction as the state change.
8. The daemon SHALL treat `succeeded` and `cancelled` as terminal task states that reject new attempts (see Requirement 5).

### Requirement 4: Attempt lifecycle and leasing

**User Story:** As an operator, I want each attempt to record a lease that a heartbeat refreshes, so that a stuck attempt is detectable.

#### Acceptance Criteria

1. WHEN an attempt begins THEN the daemon SHALL create an `attempts` row with a ULID `id`, the parent `task_id`, a 1-based `attempt_no` unique per task, `state = 'running'`, `started_at = now`, and `prompt_hash = sha256(task.spec)` computed at attempt start. The daemon SHALL create this attempt row (and emit `attempt.started`, Requirement 4.2) **in the same transaction as the atomic task claim** (Requirement 12.13), and SHALL create the attempt's git worktree **only after that transaction commits** (HIGH-4). This attempt-row-first ordering guarantees that a pre-session setup/spawn failure — which occurs before any worktree exists — still has an attempt row to record its outcome against (Requirement 22.7a).
1a. **Setup window — definition.** The *setup window* is the interval from the atomic task claim (Requirement 12.13, which sets `attempts.state = 'running'` with `pid IS NULL`) until the spawner records the agent process identity (`attempts.pid IS NOT NULL`). During this window `attempts.pid IS NULL`. An API `cancel` (Requirement 5.4), a circuit-breaker cancel (Requirement 12.9), the lease checker (Requirement 4.5), and the idle-timeout enforcer (Requirement 17.6) can all fire while the window is open, and the five rules below (Rules 1–5) are the single, canonical state machine that resolves every race across that window. `teardownAttempt` (Requirement 16.10) performs the running→ended transition and NEVER inspects `termination_intent`; `termination_intent` is consumed by the callers (Rules 1, 3), not by `teardownAttempt`.

   **RULE 1 — Cancel / circuit-breaker during the setup window.** The cancel/breaker caller SHALL atomically set `termination_intent = { outcome, reasonCode, failureClass }` (compare-and-set: only set if currently null — first-writer-wins, Rule 4). THEN it SHALL read `pid` from the attempt row (`SELECT pid FROM attempts WHERE id = ?`). IF `pid IS NOT NULL` THEN the caller SHALL call `teardownAttempt(attempt_id, intent, /* skipKill */ false)`. IF `pid IS NULL` THEN the caller SHALL return (`202`); it SHALL NOT call `teardownAttempt` (Rule 3 will consume the intent on the pid record). This SET-INTENT-FIRST-THEN-READ-PID ordering avoids the TOCTOU race in which the spawner records the pid between the read and the set.

   **RULE 2 — Lease checker and idle-timeout enforcer during the setup window.** For an attempt with `pid IS NULL`: IF `now() < started_at + setup_timeout_s × 1000` (default `setup_timeout_s = 120`) THEN the checker SHALL SKIP the attempt entirely — it SHALL NOT set `termination_intent` and SHALL NOT call `teardownAttempt`; the open setup window protects against a false lease expiry. IF `now() >= started_at + setup_timeout_s × 1000` (the setup has hung) THEN the checker SHALL set `endState = termination_intent ?? { outcome: 'failed', reasonCode: 'spawn_failed', failureClass: 'infra' }` and call `teardownAttempt(attempt_id, endState, /* skipKill */ false)` — `skipKill = false` because at setup-window expiry the agent process MAY already be alive (the spawn may have completed but the pid-record UPDATE of Rule 3 not yet committed), so `teardownAttempt` MUST run its SIGTERM/SIGKILL/ACP-close kill steps to reap any such process; when `pid IS NULL` those kill steps are internally skipped anyway (Requirement 16.10 Step 1), and worktree cleanup still runs regardless.

   **RULE 3 — Spawner records the pid (setup succeeds).** Immediately after spawning the agent, the spawner SHALL record the process identity (`pid`, `pgid`, `process_start_time`, `process_cmdline`; Requirement 13.11) AND refresh the lease in the SAME transaction via a conditional UPDATE `UPDATE attempts SET pid = ?, pgid = ?, process_start_time = ?, process_cmdline = ?, lease_expires_at = (? + 3 × heartbeat_interval_ms) WHERE id = ? AND state = 'running'`, where the `?` inside the `lease_expires_at` expression is `now()` in ms. Refreshing `lease_expires_at` to `now() + 3 × heartbeat_interval_ms` when the pid is recorded (rather than leaving it anchored to `started_at`) prevents a premature lease expiry — the default lease (90 s) would otherwise elapse before the setup budget (`setup_timeout_s = 120 s`), because heartbeats do not begin until after the agent spawns. IF that UPDATE affects **0 rows** THEN the attempt was already ended by Rule 2 (the setup window expired): the spawner SHALL kill its own just-spawned child (`kill(pgid, SIGKILL)`), run `git worktree remove --force` on the worktree it created, and return WITHOUT sending the initial prompt and WITHOUT re-checking `termination_intent`. IF the UPDATE affects **1 row** THEN the spawner SHALL check `termination_intent`: IF it is set THEN the spawner SHALL call `teardownAttempt(attempt_id, termination_intent, /* skipKill */ false)` and SHALL NOT send the initial prompt; IF it is unset THEN the spawner SHALL proceed — send the preamble + `spec` prompt (Requirement 23) and disarm the `setup_timeout_s` timer (Rule 5).

   **RULE 4 — `termination_intent` is set-once (first-writer-wins).** Setting `termination_intent` SHALL be a conditional update or in-memory compare-and-set so that only the first caller wins; subsequent callers SHALL skip silently. This arbitrates a concurrent cancel + lease race during the setup window.

   **RULE 5 — `setup_timeout_s` timer disarm.** The `setup_timeout_s` timer is disarmed atomically when the spawner's conditional UPDATE of Rule 3 succeeds with 1 row. Any timeout that fires after the disarm is a no-op.

   Together Rules 1–5 close every race across the setup window: a cancel during setup (Rule 1 — set intent, no teardown); a timeout during setup (Rule 2 — teardown with `skipKill = false` after `setup_timeout_s`, reaping any process that spawned before the window expired); a pid recorded after a cancel (Rule 3 — 1-row UPDATE then teardown with the intent); a pid recorded in a race against a timed-out teardown (Rule 3 — 0-row UPDATE, spawner kills its own child); a lease/idle check during setup (Rule 2 — skip while the window is open); and a concurrent cancel + lease (Rule 4 — first writer wins).
1b. **Partial-worktree cleanup on spawn failure (HIGH-3).** IF worktree creation, GitHub setup validation, or the agent spawn fails after the claim (ending the attempt `spawn_failed`/`auth_failed`/`rate_limited`), the worktree MAY be only partially created. The teardown of such an attempt SHALL remove the worktree with `git worktree remove --force` (Requirement 16.10 step 2) so a half-created worktree is cleaned up rather than left orphaned.
1c. **Bounded setup window — config `setup_timeout_s` (default `120`).** A stuck setup step (e.g. `git worktree add` blocked on a lock, or a GitHub setup token fetch that never returns) must never hold a repo slot forever. The spawner SHALL wrap the entire setup phase — from worktree creation through the agent spawn — in a `try/finally` governed by a `setup_timeout_s` deadline. IF the setup phase exceeds `setup_timeout_s` OR any setup step returns an error THEN the attempt SHALL be ended by calling `teardownAttempt(attempt_id, termination_intent ?? { outcome: 'failed', reasonCode: 'spawn_failed', failureClass: 'infra' }, /* skipKill */ false)` — `skipKill = false` because a setup-timeout hang (as opposed to a pre-session spawn/auth/rate_limit failure where no process was ever created) may leave an agent process alive, so `teardownAttempt` MUST run its kill steps to reap it; those steps are internally skipped when `pid IS NULL`, and worktree cleanup runs regardless. A setup still hung past the deadline is independently reaped by Rule 2 of Requirement 4.1a (the lease checker or idle-timeout enforcer tears it down once `now() >= started_at + setup_timeout_s × 1000`), and the spawner's conditional pid UPDATE (Rule 3) handles the lost race if its setup completes after that teardown.
2. WHEN an attempt begins THEN the daemon SHALL emit an `attempt.started` event carrying `attempt_no`, `agent`, `model`, and `agent_version`, in the same transaction as the `attempts` insert.
3. WHEN an attempt is running THEN the daemon SHALL periodically emit `attempt.heartbeat` events at an interval defaulting to 30 seconds and configurable via `budget.heartbeat_interval_s`, each carrying `last_activity_ts`, `turns_so_far`, and `tokens_so_far`.
4. WHEN an attempt begins THEN the daemon SHALL set `attempts.lease_expires_at = now() + (3 × heartbeat_interval_s × 1000)`, and on **every** `attempt.heartbeat` event THEN the daemon SHALL refresh it to `now() + (3 × heartbeat_interval_s × 1000)`, in the same transaction as the heartbeat event write. The lease is therefore anchored to the last heartbeat (i.e. `now()` at refresh time), NOT to `started_at`; so the lease expires three heartbeat intervals after the *last* heartbeat, not three intervals after the attempt started. This lease window of three heartbeat intervals tolerates up to two consecutive missed heartbeats before the lease is considered expired.
5. The daemon SHALL run a background lease checker on an interval of `heartbeat_interval_s`. The lease checker is a Rule 2 caller of Requirement 4.1a. IF the checker finds a `state = 'running'` attempt with `pid IS NULL` (still in the setup window) THEN it SHALL apply Rule 2 — SKIP the attempt while `now() < started_at + setup_timeout_s × 1000`, and once `now() >= started_at + setup_timeout_s × 1000` tear it down with `endState = termination_intent ?? { outcome: 'failed', reasonCode: 'spawn_failed', failureClass: 'infra' }` and `skipKill = false` (at window expiry the agent process may already be alive; `teardownAttempt` internally skips its kill steps when `pid IS NULL`). IF the checker finds a `state = 'running'` attempt with `pid IS NOT NULL` whose `lease_expires_at` is in the past THEN the daemon SHALL end that attempt through the single `teardownAttempt` path (Requirement 16.10) with `outcome = 'interrupted'`, `failure_class = 'infra'`, `reason_code = 'interrupted'`, `skipKill = false` — which kills the still-running agent process (not just the DB row) and emits `attempt.ended`.
6. WHEN an attempt ends THEN the daemon SHALL set `attempts.state = 'ended'`, set `ended_at = now`, and persist the full outcome payload (Requirement 6) in the same transaction as the `attempt.ended` event.
7. The daemon SHALL enforce `UNIQUE(task_id, attempt_no)` on the `attempts` table.

### Requirement 5: Retry and cancel

**User Story:** As an orchestrator, I want to explicitly request a retry or a cancel, so that the daemon never retries on its own and never leaves orphaned work on cancel.

#### Acceptance Criteria

1. WHEN a client sends `POST /v1/tasks/:id/attempts` AND the task is in state `failed` or `blocked` THEN the daemon SHALL transition the task back to `queued`, emit a `task.requeued` event with `reason = 'retry'` in the same transaction (Requirement 8.7), and return `202` with the task; the daemon SHALL NOT create an attempt row directly. The new attempt row (with `attempt_no` = previous max + 1) SHALL be created only when the `RepoScheduler` fires and claims the task (via the atomic conditional UPDATE of Requirement 12.13), so that the per-repo concurrency guard (Requirement 12.2) and the circuit breaker (Requirement 12.6) are always respected on retry.
2. IF the task is in state `queued`, `running`, `succeeded`, or `cancelled` THEN `POST /v1/tasks/:id/attempts` SHALL return `409` with `error.code = 'conflict'` and SHALL NOT re-queue the task.
3. The daemon SHALL NOT create a retry attempt automatically; a retry SHALL be requested only via an explicit `POST /v1/tasks/:id/attempts` call, and the resulting attempt SHALL still be started only by the scheduler. This rule applies to **every** failure mode, including `interrupted` ends from crash recovery or lease expiry: an interrupted task lands in `failed` with `reason_code = 'interrupted'` and waits for an explicit retry — it is never re-queued automatically (Requirement 13.9). This closes the crash-loop hole where a poison-pill task that crashes the daemon on every pickup would be re-run forever.
4. WHEN a client sends `POST /v1/tasks/:id/cancel` for a task with a running attempt THEN the daemon SHALL apply Rule 1 of Requirement 4.1a with `intent = { outcome: 'cancelled', reasonCode: 'cancelled_by_api', failureClass: null }`: it SHALL atomically set `termination_intent = intent` FIRST (compare-and-set: only set if currently null — first-writer-wins, Rule 4), THEN read `pid` from the attempt row; IF `pid IS NOT NULL` THEN the daemon SHALL call `teardownAttempt(attempt_id, intent, /* skipKill */ false)` (Requirement 16.10) directly to kill the agent session (close the ACP connection, `SIGTERM`, 5-second grace, then `SIGKILL`; Requirement 16.7), clean up the attempt's worktree, set the attempt outcome to `cancelled` with `reason_code = 'cancelled_by_api'`, transition the task to `cancelled`, and emit `attempt.ended` and `task.cancelled` events. IF `pid IS NULL` (the attempt is still in the setup window) THEN the daemon SHALL return `202` and NOT call `teardownAttempt` — Rule 3 consumes the intent on the pid record, i.e. the spawner's Rule 3 re-check performs the real teardown once the `pid` exists. Setting the intent BEFORE reading `pid` avoids the TOCTOU race in which the spawner records the pid between the read and the set. In both the setup-window and the running case the attempt ultimately ends `cancelled`/`cancelled_by_api` through the single `teardownAttempt` path.
5. WHEN a client sends `POST /v1/tasks/:id/cancel` for a task with no running attempt (e.g. `queued`, `failed`, `blocked`) THEN the daemon SHALL transition the task to `cancelled` and emit `task.cancelled` without emitting `attempt.ended`.
6. IF the task is already in a terminal state (`succeeded`, `cancelled`) THEN `POST /v1/tasks/:id/cancel` SHALL return `409` with `error.code = 'conflict'`.
7. WHEN `task.cancelled` is emitted THEN its `data` SHALL include `by` (`'api'` for an API cancel) and `reason`.

### Requirement 6: Outcome contract

**User Story:** As an orchestrator, I want a closed, versioned outcome and reason-code enum per attempt, so that I can branch on structured values rather than prose.

#### Acceptance Criteria

1. The daemon SHALL constrain attempt `outcome` to the closed union: `succeeded | failed | blocked | cancelled | timed_out | budget_exceeded | interrupted`.
2. The daemon SHALL set `attempts.failure_class = 'infra'` when `outcome = 'failed'` with an infrastructure cause OR when `outcome = 'interrupted'`; for all other outcomes `failure_class` SHALL be `NULL`.
3. The daemon SHALL set `failure_class = 'infra'` in exactly two cases, and `NULL` in every other case:
   - WHEN `outcome = 'failed'` with an infrastructure cause — `reason_code ∈ { spawn_failed, auth_failed, rate_limited, git_push_failed, adapter_crash, cancelled_by_breaker }` — THEN `failure_class = 'infra'`; for all other `failed` causes (`agent_reported_failure`, `no_changes`, `agent_error`) `failure_class = NULL`.
   - WHEN `outcome = 'interrupted'` (`reason_code = 'interrupted'`, set by the lease checker or restart recovery) THEN the daemon SHALL also set `failure_class = 'infra'`.

   This covers both `outcome = 'failed'` (infra cause) and `outcome = 'interrupted'`; the two together are the only outcomes for which `failure_class` is ever non-NULL, consistent with Requirements 6.8 and 12.9.
4. The daemon SHALL constrain `reason_code` to the closed, versioned enum: `spawn_failed, auth_failed, rate_limited, git_push_failed, adapter_crash, no_changes, agent_reported_failure, agent_error, agent_blocked, budget_exceeded, timed_out, interrupted, cancelled_by_api, cancelled_by_breaker`. The daemon SHALL allow `reason_code = NULL` when `outcome = 'succeeded'`.
5. The daemon SHALL allow a free-text `reason` string for human consumption, distinct from the closed `reason_code`.
6. WHEN an attempt ends THEN the daemon SHALL persist `artifacts` (JSON: `branch`, `base_sha`, `head_sha`, `pr_url`, `diff_stats`, `transcript_ref`), `usage` (JSON: `wall_ms`, optional `input_tokens`, `output_tokens`, `cost_usd`), `agent_version`, and `model` where available.
7. WHEN `outcome = 'blocked'` THEN the `attempt.ended` event `data` SHALL include a `blocked` object with `question` (string) and `needs` (one of `credential | decision | access | other`), and the daemon SHALL persist that object as JSON in the `attempts.blocked` column.
7a. The `attempts.blocked` column SHALL be declared `TEXT DEFAULT NULL`. The daemon SHALL set it to the JSON `{ question, needs }` object **only** when `outcome = 'blocked'`; for every other outcome (`succeeded`, `failed`, `cancelled`, `timed_out`, `budget_exceeded`, `interrupted`) the column SHALL be `NULL`.
8. The daemon SHALL set `reason_code` consistently with `outcome` according to the following closed mapping. `reason_code` is `NULL` only for `succeeded`:

   | `outcome` | permitted `reason_code` | `failure_class` |
   |---|---|---|
   | `succeeded` | `NULL` | `NULL` |
   | `failed` | one of `spawn_failed`, `auth_failed`, `rate_limited`, `git_push_failed`, `adapter_crash`, `no_changes`, `agent_reported_failure`, `agent_error`, `cancelled_by_breaker` | `'infra'` for `spawn_failed`/`auth_failed`/`rate_limited`/`git_push_failed`/`adapter_crash`/`cancelled_by_breaker`; `NULL` for `no_changes`/`agent_reported_failure`/`agent_error` |
   | `blocked` | `agent_blocked` | `NULL` |
   | `cancelled` | `cancelled_by_api` | `NULL` |
   | `timed_out` | `timed_out` | `NULL` |
   | `budget_exceeded` | `budget_exceeded` | `NULL` |
   | `interrupted` | `interrupted` | `'infra'` |

   Note: a circuit-breaker-induced cancel does not produce `outcome = 'cancelled'`; it produces `outcome = 'failed'` with `reason_code = 'cancelled_by_breaker'` (Requirement 12.9).

### Requirement 7: Agent outcome channel

**User Story:** As the daemon, I want to learn the agent's self-declared outcome through structured channels, so that I never parse free-text final messages.

#### Acceptance Criteria

1. The daemon SHALL expose a `report_outcome` tool via the MCP/ACP tool surface accepting `{ outcome, reason_code, reason, blocked?, pr_url? }`, where `pr_url` is an OPTIONAL string validated as a URL (HIGH-6). WHEN `pr_url` is supplied THEN the daemon SHALL persist it into `artifacts.pr_url` (Requirement 16.5); WHEN it is absent THEN `artifacts.pr_url` SHALL be `NULL`.
1a. The `report_outcome` tool and the `.agent-router/outcome.json` file SHALL only accept an `outcome` value of `'succeeded'`, `'failed'`, or `'blocked'`. The daemon-side outcomes `timed_out`, `budget_exceeded`, `interrupted`, and `cancelled` are set exclusively by the router; the agent SHALL NOT be able to declare or override them. IF the agent supplies any other `outcome` value THEN the daemon SHALL reject the self-report and fall through to mechanical classification (Requirement 7.7).
2. WHEN the agent calls `report_outcome` with a valid payload THEN the daemon SHALL record that payload as the attempt's declared outcome (preferred source).
2a. **`pr_url` wire forwarding (HIGH-5).** The `pr_url` field SHALL survive the full hop from the agent to the stored attempt row, not merely appear in the MCP tool schema (Requirement 7.1). Specifically: (1) `mcp-server.ts`'s `tools/call` handler SHALL include `pr_url` in the Unix-socket message it forwards to the daemon — the wire payload SHALL be `{ op: 'report_outcome', session_id, outcome, reason_code, reason, blocked, pr_url }`; (2) the daemon's socket handler (`cli-server.ts` → the active `AttemptRunner`) SHALL extract `pr_url` from the call arguments and record it on the attempt's in-memory declared-outcome state; and (3) at attempt end the daemon SHALL copy that `pr_url` into `endState.artifacts.pr_url` (Requirement 16.10 / HIGH-1), so it is persisted in `artifacts.pr_url` and surfaced on `GET /v1/attempts/:id` (Requirement 10.1). WHEN `pr_url` is absent in the agent's call THEN `artifacts.pr_url` SHALL be `NULL`. The identical flow applies to a `pr_url` read from a valid `.agent-router/outcome.json`.
3. WHEN the agent does NOT call `report_outcome` THEN the daemon SHALL look for a `.agent-router/outcome.json` file in the worktree root on pickup and SHALL schema-validate it before accepting it.
4. IF `.agent-router/outcome.json` is present but fails schema validation THEN the daemon SHALL ignore it and fall through to mechanical classification.
5. IF neither `report_outcome` nor a valid `.agent-router/outcome.json` is available THEN the daemon SHALL mechanically classify the outcome from the session exit code and worktree state per the classification table in Requirement 16.3 (e.g. no diff → `no_changes`, nonzero exit → `agent_error`).
6. The daemon SHALL NOT infer outcome by parsing the agent's free-text final message under any circumstance.
7. WHEN `report_outcome` or `outcome.json` supplies an `outcome` or `reason_code` outside the closed enums THEN the daemon SHALL reject that value and fall through to mechanical classification.

### Requirement 8: Event envelope and types

**User Story:** As a consumer of the event stream, I want every event to share one envelope and a known set of Tier 1 types, so that I can process events generically.

#### Acceptance Criteria

1. The daemon SHALL write every event to `task_events` with a monotonically increasing integer `seq` (AUTOINCREMENT primary key), a ULID `id`, `ts` (unix ms), `type`, optional `repo`/`task_id`/`attempt_id`, and a JSON `data` blob.
2. WHEN an event is serialized to a client THEN the envelope SHALL contain: `v` (= 1), `seq`, `id`, `ts` (ISO 8601), `type`, `repo`, `task_id`, `attempt_id`, `external_id`, `metadata`, and `data`.
3. WHEN an event belongs to a task that has an `external_id` THEN the serialized envelope SHALL include that `external_id`; otherwise `external_id` SHALL be `null`.
4. WHEN an event belongs to a task that has `metadata` THEN the serialized envelope SHALL echo that `metadata` verbatim; otherwise `metadata` SHALL be an empty object or `null`.
5. The daemon SHALL support these Tier 1 event types and `data` shapes:
   - `daemon.started` → `version`, `interrupted_attempt_ids[]`
   - `task.queued` → `source`, `title`
   - `task.requeued` → `reason` (`"retry" | "interrupted" | "importer"`)
   - `task.cancelled` → `by` (`"api" | "breaker"`), `reason`
   - `attempt.started` → `attempt_no`, `agent`, `model`, `agent_version`
   - `attempt.heartbeat` → `last_activity_ts`, `turns_so_far`, `tokens_so_far`
   - `attempt.ended` → full outcome payload (Requirement 6)
   - `repo.paused` → `reason`, `consecutive_failures`
   - `repo.resumed` → `reset_by` (`"api" | "auto"`), `reason`
6. The daemon SHALL NOT emit Tier 2 event types (`pr.opened`, `pr.checks_completed`, `pr.closed`) as part of this feature.
7. The daemon SHALL emit a `task.requeued` event WHENEVER a task moves back to `state = 'queued'` for any reason (HIGH-9). Its `data` SHALL carry `reason` ∈ `{ 'retry', 'interrupted', 'importer' }`: `'retry'` for an explicit `POST /v1/tasks/:id/attempts` re-queue (Requirement 5.1), `'interrupted'` for the `allow_resume = true` restart-resume path that returns an interrupted task to `queued` so the scheduler can start a resume attempt (Requirement 13.6, HIGH-5(a)), and `'importer'` for a ROADMAP re-submission that re-queues. The `task.requeued` event SHALL be written in the **same SQLite transaction** as the state update that re-queues the task (Requirement 15.1).

### Requirement 9: Event stream (SSE) with replay

**User Story:** As a UI, I want to subscribe to the event stream and resume after a disconnect without missing or duplicating events, so that I can render live state reliably.

#### Acceptance Criteria

1. WHEN a client sends `GET /v1/events` THEN the daemon SHALL respond with `Content-Type: text/event-stream` and stream events as Server-Sent Events, each with the event `id` set to the event's `seq`.
2. WHEN a client supplies a `Last-Event-ID` header with value N THEN the daemon SHALL replay all events with `seq > N` before streaming new events.
3. WHEN a client supplies `?since=<seq>` THEN the daemon SHALL replay all events with `seq > <seq>`; WHEN both `Last-Event-ID` and `?since` are present THEN the daemon SHALL use the larger of the two.
4. WHEN new events are written while a client is subscribed THEN the daemon SHALL deliver them in strictly increasing `seq` order and SHALL NOT deliver the same `seq` twice to a given client.
5. WHEN the connection is idle THEN the daemon SHALL send periodic SSE heartbeat/comment lines to keep the connection open through proxies.
6. IF `?since` is not a non-negative integer THEN the daemon SHALL return `400` with `error.code = 'invalid_param'`.

### Requirement 10: Attempt detail and transcript

**User Story:** As a UI, I want attempt detail and the raw transcript, so that I can show artifacts and let a human read what the agent did.

#### Acceptance Criteria

1. WHEN a client sends `GET /v1/attempts/:id` for an existing attempt THEN the daemon SHALL return `200` with the attempt fields and parsed `artifacts`/`usage`, and `"v": 1`. WHEN the attempt ended `blocked` THEN the response SHALL include a `blocked` field with the stored `{ question, needs }` object; otherwise `blocked` SHALL be `null`. The canonical storage location of the PR URL is `artifacts.pr_url` (inside the `artifacts` JSON), consistent with the `attempt.ended` event payload (Requirement 6.6); for convenient access the response SHALL ALSO surface `pr_url` as a top-level field equal to `artifacts.pr_url` (or `null` when absent). The top-level field is a convenience mirror of the value in `artifacts`, not a second source of truth.
2. IF the attempt id does not exist THEN the daemon SHALL return `404` with `error.code = 'not_found'`.
3. WHEN a client sends `GET /v1/attempts/:id/transcript` AND the transcript is active (raw on disk) THEN the daemon SHALL stream the raw transcript directly.
4. WHEN a client sends `GET /v1/attempts/:id/transcript` AND the transcript has been archived (zstd-compressed) THEN the daemon SHALL decompress it transparently and return the raw content.
5. IF the transcript has been deleted (past its TTL) THEN the daemon SHALL return `404` with `error.code = 'not_found'`.

### Requirement 11: Transcript retention (two-phase)

**User Story:** As an operator, I want transcripts kept for up to 90 days (the default compressed retention period) but eventually purged, so that disk usage stays bounded without losing recent history.

#### Acceptance Criteria

1. WHILE an attempt is active or recently ended THE daemon SHALL keep the raw `stream.log` transcript on disk and serve it directly.
2. WHEN an attempt has ended AND a configurable grace period has elapsed THEN the daemon SHALL compress the transcript with zstd (archived phase) and record its archived location in `artifacts.transcript_ref`.
3. WHEN a transcript has been archived AND a longer, separately configurable TTL has elapsed THEN the daemon SHALL delete the archived transcript (deleted phase).
4. The daemon SHALL keep the transcript-retention TTL independent of the existing agent-run directory reaper TTL.
5. WHEN an archived transcript is requested via the transcript endpoint THEN the daemon SHALL decompress zstd transparently (Requirement 10.4).

### Requirement 12: Per-repo concurrency and circuit breaker

**User Story:** As an operator, I want a configurable per-repo concurrency limit and an automatic circuit breaker, so that one failing repo cannot consume all capacity or thrash.

#### Acceptance Criteria

1. The daemon SHALL default to 1 concurrent running attempt per repo and SHALL allow the limit to be configured per repo.
2. WHILE a repo is at its concurrency limit THE daemon SHALL keep additional tasks for that repo in `queued` state until a slot frees.
3. WHEN a client sends `GET /v1/repos/:owner/:name/status` THEN the daemon SHALL return `200` and `"v": 1` with a single repo-status object in the canonical flat shape of Requirement 21.2 (`repo`, `circuit_breaker_state`, `consecutive_failures`, `paused_until`, `slots_total`, `slots_in_use`).
4. WHEN consecutive attempt failures for a repo reach a configured threshold THEN the daemon SHALL open the circuit breaker (pause the repo), stop starting new attempts for it, and emit a `repo.paused` event with `reason` and `consecutive_failures`.
5. The daemon SHALL increment a repo's `consecutive_failures` counter ONLY for attempts that end with `reason_code` in the set `{ spawn_failed, auth_failed, rate_limited, git_push_failed, adapter_crash }`. The daemon SHALL NOT increment the counter for `cancelled_by_api`, `cancelled_by_breaker`, `timed_out`, `budget_exceeded`, `interrupted`, or `no_changes`. ONE carve-out within the increment set (HIGH-7): a `git_push_failed` end caused by a **failed `git ls-remote` call itself** (`remoteBranchExists = null`, a transient network/transport error — Requirement 22.5/22.8) SHALL NOT increment the counter, because a transient remote-check failure is not a repeatable fault that should open the breaker; a `git_push_failed` from a genuinely absent or SHA-mismatched remote branch (`remoteBranchExists = false`) still increments it. In particular, `interrupted` is explicitly excluded because it reflects infrastructure instability from a daemon restart or lease expiry — not agent quality — so counting it would wrongly pause a healthy repo after routine daemon restarts (Requirement 13.10). An attempt ending with `outcome = 'succeeded'` SHALL reset the counter to 0.
6. WHEN the circuit breaker is open AND a pending task would otherwise start THEN the daemon SHALL leave it queued and SHALL NOT start an attempt.
7. WHEN a client sends `POST /v1/repos/:owner/:name/circuit-breaker/reset` THEN the daemon SHALL close the breaker, resume the repo, and emit a `repo.resumed` event with `reset_by = 'api'`.
8. WHEN the breaker resumes automatically (e.g. after a cooldown) THEN the daemon SHALL emit `repo.resumed` with `reset_by = 'auto'`.
9. IF a cancel occurs because the breaker opened THEN the daemon SHALL apply Rule 1 of Requirement 4.1a with `intent = { outcome: 'failed', reasonCode: 'cancelled_by_breaker', failureClass: 'infra' }`: it SHALL FIRST atomically set `termination_intent = intent` (compare-and-set: only set if currently null — first-writer-wins, Rule 4), THEN read the affected attempt's `pid` (`SELECT pid FROM attempts WHERE id = ?`); IF `pid IS NOT NULL` THEN the daemon SHALL call `teardownAttempt(attempt_id, intent, /* skipKill */ false)` (Requirement 16.10) directly; IF `pid IS NULL` (the attempt is still in the setup window) THEN the daemon SHALL return, NOT calling `teardownAttempt` — the spawner's Rule 3 re-check consumes the already-set intent and performs the real teardown once the `pid` exists. This SET-INTENT-FIRST-THEN-READ-PID ordering (matching Requirement 5.4 and Rule 1 of Requirement 4.1a) avoids the TOCTOU race in which the spawner records the pid between the read and the set — were the pid read first, a pid recorded in that gap would leave the breaker caller believing the attempt was still pidless (so it would skip teardown) while the spawner's Rule 3 re-check would find no intent yet set, orphaning the process. In either the setup-window or the running case the affected attempt SHALL end with `outcome = 'failed'`, `failure_class = 'infra'`, and `reason_code = 'cancelled_by_breaker'`, so that the task transitions to `failed` and remains eligible for retry. Setting the intent first guarantees that even if the agent's ACP returns `stopReason = 'cancelled'` during teardown, the attempt is still classified `failed`/`cancelled_by_breaker` (not terminal `cancelled`), because `resolveOutcome` honors the termination intent before the ACP stop reason (Requirement 16.8). The breaker-induced cancel SHALL NOT itself increment `consecutive_failures` (Requirement 12.5).
10. WHEN any attempt for a repo completes with `outcome = 'succeeded'` THEN the daemon SHALL reset that repo's `consecutive_failures` to `0`, AND IF the breaker was `open` or `half-open` THEN the daemon SHALL set `circuit_breaker_state` to `closed` and emit a `repo.resumed` event with `reset_by = 'auto'`. (This is the success-driven auto-reset: a repo recovers automatically the moment a real success lands.)
11. The breaker state SHALL be the closed union `closed | open | half-open`. The daemon MAY support a time-based probe: after `circuit_breaker_timeout_s` (configurable, default `3600`) has elapsed since the repo's `paused_at`, the daemon MAY move the breaker from `open` to `half-open` and allow exactly one probe attempt to start; IF that probe attempt completes `succeeded` THEN the breaker closes (per Requirement 12.10) and `repo.resumed` (`reset_by = 'auto'`) is emitted; IF the probe fails with an infra reason code THEN the breaker returns to `open` and `paused_at` is reset. WHILE `half-open`, the daemon SHALL allow exactly one in-flight probe attempt (concurrent_probe_limit = 1).
12. The daemon SHALL persist `paused_at` (unix ms, when the breaker last opened) alongside the breaker state so the time-based probe window survives a restart.
13. The scheduler SHALL claim a `queued` task with a conditional UPDATE: `UPDATE tasks SET state = 'running' WHERE id = ? AND state = 'queued'`. IF `0` rows are updated THEN the task was already claimed by a concurrent scheduler pass or was cancelled, and the scheduler SHALL skip it (no attempt row created). This makes task claiming atomic at the database level (HIGH-8).
14. The scheduler SHALL additionally maintain an in-memory `claiming` set of task ids it is currently dispatching, and SHALL NOT dispatch a task whose id is already in that set, so that a single process cycle cannot double-dispatch the same task before the conditional UPDATE commits. The id is added to `claiming` before the UPDATE and removed after the attempt row is created (or the claim fails).

### Requirement 13: Restart (crash recovery) semantics

**User Story:** As an operator, I want the daemon to recover cleanly from a crash, so that attempts that were running at crash time are marked `interrupted` and optionally resumed.

#### Acceptance Criteria

1. WHEN the daemon starts THEN it SHALL find all `attempts` rows WHERE `state = 'running'`. It SHALL ALSO sweep `tasks` rows WHERE `state = 'running'` that have NO attempt in `state = 'running'` (HIGH-4 — a task claimed but left without a live attempt by a torn write) and mark each such task `interrupted` → `failed` with `reason_code = 'interrupted'` (per Requirement 13.9, no auto-retry), in the same recovery pass. Under normal operation the atomic claim-and-create of Requirement 4.1 / 22.7a (task claim and attempt insert in one transaction) prevents this state; the sweep is a belt-and-suspenders guard so no task is stranded in `running` with nothing driving it.
2. WHEN a running attempt is found at startup THEN the daemon SHALL mark it `state = 'ended'`, `outcome = 'interrupted'`, `failure_class = 'infra'`, `reason_code = 'interrupted'`, and set `ended_at = now`.
3. WHEN each interrupted attempt is marked THEN the daemon SHALL emit an `attempt.ended` event for it.
4. WHEN restart recovery completes THEN the daemon SHALL emit a single `daemon.started` event whose `data.interrupted_attempt_ids` lists the ids of all attempts interrupted during this startup, and whose `data.version` records the daemon version.
5. `budget.allow_resume` SHALL default to `false`. WHEN it is absent or `false` THEN restart recovery SHALL mark the attempt `interrupted` (as above) and SHALL NOT attempt to resume the agent session; this is session-state recovery only. The parent task transitions to `failed` with `reason_code = 'interrupted'` (Requirement 13.9) and is NOT re-queued automatically; the orchestrator or operator retries explicitly via `POST /v1/tasks/:id/attempts` (Requirement 5.1), or cancels via Requirement 5. (An explicit retry starting a fresh attempt is distinct from resuming the crashed session, which requires `allow_resume = true`; see Requirement 13.6.)
6. WHEN `budget.allow_resume` is `true` the daemon SHALL support resuming the interrupted session, subject to the following rules (HIGH-5):
   - **Agent support:** `allow_resume` is only supported for `agent = 'kiro'` (via `kiro-cli --resume-id`). For `agent = 'claude'` the daemon SHALL log a warning and treat `allow_resume` as `false` (Claude Code has no equivalent resume mechanism).
   - **Session id:** the daemon SHALL store the interrupted session's id in a new column `tasks.resume_session_id TEXT` when the session is interrupted.
   - **Worktree:** WHEN `outcome = 'interrupted'` AND `task.allow_resume = true` THEN the daemon SHALL skip worktree removal (the Requirement 18.4 exception) so the resumed session can continue in the same worktree.
   - **Worktree-existence precondition (HIGH-5(d)):** before attempting a resume, the daemon SHALL verify that the attempt's worktree path still exists on disk. IF it does NOT exist (e.g. `/tmp` was cleared across the restart) THEN the daemon SHALL fall back to the `allow_resume = false` behavior — leave the task `failed`/`interrupted` (Requirement 13.9) for a fresh explicit retry — and SHALL NOT attempt the resume.
   - **Re-queue before claim (HIGH-5(a)):** a resume SHALL go through the scheduler like any other work. On startup, WHEN `allow_resume = true` AND `tasks.resume_session_id IS NOT NULL` AND the worktree exists, the daemon SHALL move the task to `state = 'queued'` and emit a `task.requeued` event with `reason = 'interrupted'` (Requirement 8.7) in the same transaction, INSTEAD OF leaving it `failed`. The scheduler then claims the queued task through the normal atomic claim (Requirement 12.13), so resume honors the per-repo concurrency guard (Requirement 12.2) and the breaker and never bypasses the scheduler.
   - **Resume attempt reuses the original branch (HIGH-5(c)):** when the scheduler claims the re-queued task, the daemon SHALL create a NEW attempt row (`attempt_no` = previous max + 1) whose `session_id = tasks.resume_session_id`, marked `resuming`, that **reuses the SAME branch `agent/<original_attempt_id>`** (the interrupted attempt's branch) rather than minting a new `agent/<new_attempt_id>` branch. All git operations for the resume — including the post-exit `git ls-remote origin refs/heads/agent/<original_attempt_id>` push check (Requirement 22.5) — SHALL target that original branch, so the remote-ref/SHA comparison checks the branch the agent actually pushed to and cannot produce a false `git_push_failed`.
   - **Clear `resume_session_id` after one use (HIGH-5(b)):** WHEN the resume attempt row is created, the daemon SHALL set `tasks.resume_session_id = NULL` (one resume per interruption). This prevents a repeated crash loop: if the resumed attempt itself is interrupted again, it does not auto-resume a second time off the same stale session id — it falls back to `failed`/`interrupted` awaiting an explicit retry.
   - **Concurrency / abandonment:** only one concurrent resume attempt per task is allowed. IF a slot is not available within the 30-second resume window, or resume otherwise fails to come up, THEN the daemon SHALL abandon the resume; the task remains `failed`/`interrupted` (Requirement 13.9) and is retried only via an explicit `POST /v1/tasks/:id/attempts`.
7. All restart-recovery state transitions and their events SHALL be written in SQLite transactions (per attempt, or batched) so a second crash cannot leave half-written recovery state.
8. WHEN the daemon starts THEN tasks already in `state = 'queued'` SHALL be retained as-is (not reset, not failed); after `daemon.started` is emitted the `RepoScheduler` SHALL resume processing them, subject to the per-repo concurrency guard and circuit breaker.
9. WHEN restart recovery (or the lease checker) marks a running attempt `interrupted` THEN the daemon SHALL set that attempt's parent task to `state = 'failed'` with the attempt's `reason_code = 'interrupted'` (NOT re-queue it automatically), EXCEPT in the single `allow_resume = true` resume case of Requirement 13.6, where the task is instead moved to `queued` with a `task.requeued`(`reason = 'interrupted'`) event so the scheduler can start a resume attempt. That exception is bounded and cannot crash-loop because `resume_session_id` is cleared after one use (Requirement 13.6, HIGH-5(b)): a second interruption of the resumed attempt falls back to `failed`/`interrupted`. The daemon SHALL NOT create a retry attempt on its own: automatic re-queueing would create a crash loop for a poison-pill task that crashes the daemon on every pickup, and it would contradict Requirement 5.3 ("the daemon SHALL NOT create a retry attempt automatically"). To retry, the orchestrator or operator calls `POST /v1/tasks/:id/attempts` (Requirement 5.1), which re-queues the task through the scheduler like any other explicit retry. (This supersedes the earlier draft that returned interrupted tasks to `queued`; it makes the restart-recovery path consistent with Requirement 5.3 and keeps retry policy in the orchestrator.) The task's `updated_at` SHALL be bumped in the same transaction as the attempt-end write.

   Note: the ROADMAP importer re-submission loop (Requirement 14) is a different flow and is unaffected — `external_id` idempotency (Requirement 1.3) prevents the importer from creating a duplicate task, and the importer never auto-retries a `failed` task.
10. The daemon SHALL NOT increment a repo's `consecutive_failures` counter for `outcome = 'interrupted'` (Requirement 12.5 already excludes it). An interruption reflects infrastructure instability from a daemon restart or lease expiry, not agent quality, so counting it toward the circuit breaker would wrongly pause a healthy repo after routine daemon restarts.
11. The `attempts` table SHALL store `pid` and `pgid` columns for the agent process, AND (HIGH-8) a `process_start_time INTEGER` column (the value of `/proc/<pid>/stat` field 22 — process start time in clock ticks since boot — captured at spawn) and a `process_cmdline TEXT` column (the agent's command-line prefix, e.g. `kiro-cli` or `node`, captured at spawn), all recorded once the agent is spawned, so that a daemon restart can find, **verify the identity of**, and reap a still-running orphan process from a previous daemon instance.
12. WHEN the daemon starts THEN it SHALL run `git worktree prune` in the repo clone **unconditionally and before iterating the running-attempts list (HIGH-2)**: `git worktree prune` is idempotent and clears any orphaned worktree registration/directory, including a half-created worktree from a process killed mid-setup (a `spawn_failed`, HIGH-3) that may have no `attempts` row at all. Then, for each attempt in `state = 'running'`, THEN it SHALL, before marking the attempt `interrupted`: (1) check whether the stored `pid` is still alive; (2) **verify the PID identity before killing (HIGH-8)** — on Linux read `/proc/<pid>/stat` field 22 (process start time) and compare it to the stored `process_start_time`, AND read `/proc/<pid>/cmdline` and verify it matches the stored `process_cmdline` prefix; IF the stored start time does NOT equal the current `/proc/<pid>/stat` field 22, OR the cmdline prefix does not match, THEN the daemon SHALL SKIP the kill (the PID was recycled to an unrelated process after a reboot) and log a warning; (3) only when BOTH identity checks pass, `SIGKILL` the process (preferring a `pgid` group kill) to reap the orphaned agent left behind by the crashed daemon; and (4) mark the attempt `interrupted` per Requirement 13.9 (task → `failed`, `reason_code = 'interrupted'`, no auto-retry) by routing through the single `teardownAttempt` path (Requirement 16.10) **with `skipKill = true`**. 

    The `skipKill = true` argument (HIGH-2) is REQUIRED on this startup path: `teardownAttempt`'s own kill steps contain the same PID-identity check, but after a reboot the stored `process_start_time` was captured against the previous boot's clock and can NEVER match the current `/proc/<pid>/stat` field 22, so leaving the kill enabled inside `teardownAttempt` would skip-and-warn on every attempt (or risk signaling a recycled PID). With `skipKill = true`, `teardownAttempt` skips its SIGTERM/SIGKILL/ACP-close steps while still running the DB end-claim, the `attempt.ended`/task-state events, and the worktree cleanup. The explicit orphan reap of (1)–(3) above — which runs OUTSIDE `teardownAttempt` and handles the crash-without-reboot case where an agent is genuinely still alive — SHALL precede the `teardownAttempt(..., skipKill=true)` call so no agent process from the previous instance survives the recovery, and so that no unrelated process is ever killed by a stale PID. The unconditional `git worktree prune` and the orphan reap both precede the `interrupted` marking.

### Requirement 14: ROADMAP.md intake adapter

**User Story:** As a maintainer, I want ROADMAP.md to become one intake adapter over task submission, so that the DB is the source of truth and the roadmap is optional rendering.

#### Acceptance Criteria

1. The daemon SHALL treat ROADMAP.md as one intake adapter that calls the same `submitTask()` path as the API — not as the primary mechanism.
2. WHEN a ROADMAP checklist line carries an annotation of the form `<!-- ar:<ULID> -->` THEN the importer SHALL derive the task's `external_id` from that annotation id (NOT from a hash of the item text).
3. WHEN a ROADMAP checklist line has no annotation on first scan THEN the importer SHALL generate an annotation id and write it back to the line, committing and **pushing** the annotation **before** calling `submitTask()` for that item. The ordering SHALL be strictly: (a) `git pull --ff-only` the roadmap branch so the scan sees the latest annotations; (b) for each unannotated item, generate the ULID and write the `<!-- ar:<ULID> -->` annotation back, committing the annotation change; (c) push the annotation commit; (d) only on a successful push, call `submitTask()` using that annotation id as `external_id`. IF the push is rejected (stale-ref conflict — another writer advanced the branch), the importer discards the local commit, runs `git pull --ff-only`, and restarts the scan (Requirement 20.8), so a second importer re-pulls and adopts the winning annotation rather than minting a competing one. Correctness against concurrent importers comes from this push-before-submit ordering — NOT from the `UNIQUE(external_id)` constraint, which would not stop two importers that each minted a *different* ULID. The `UNIQUE` constraint is only a backstop against the *same* `external_id` being submitted twice (Requirement 1.3).
4. WHEN a ROADMAP item is imported THEN the resulting task SHALL have `source = 'roadmap'` and `source_ref` recording the roadmap file path plus the item annotation id.
5. The daemon SHALL tick a ROADMAP item's checkbox only when its task reaches state `succeeded` — never when an attempt merely starts.
6. The daemon SHALL treat the database as the source of truth and ROADMAP.md as an optional rendering of task state.
7. WHEN the importer re-scans an already-annotated, already-submitted item THEN it SHALL NOT create a duplicate task (idempotent via `external_id`, Requirement 1.3).

### Requirement 15: Transactional integrity and error handling

**User Story:** As an operator, I want every state change and its event written atomically, so that the event stream can never disagree with persisted state.

#### Acceptance Criteria

1. WHEN the daemon changes task or attempt state AND emits the corresponding event THEN both writes SHALL occur in a single SQLite transaction.
2. IF a transaction fails THEN neither the state change nor the event SHALL be persisted (all-or-nothing).
3. The daemon SHALL define task/attempt-domain error types analogous to the existing `FatalError`/`EventError`/`WakeError` classes (e.g. `TaskError`, `AttemptError`) for failures scoped to a single task or attempt.
4. WHEN a task- or attempt-scoped error occurs THEN the daemon SHALL log it with the structured logger and continue running; it SHALL NOT crash the daemon for a single task's failure.
5. The daemon SHALL store the three new tables in the existing SQLite database with WAL mode and prepared statements, following the established `src/db.ts` pattern.

### Requirement 16: Success path and mechanical classification

**User Story:** As an orchestrator, I want a fully specified success path with a deterministic classification for every attempt end, so that a succeeding attempt is recorded as `succeeded` and I never have to infer success from prose.

#### Acceptance Criteria

1. The daemon SHALL consider an attempt ended WHEN the agent session reports an ACP `stopReason` OR the agent process exits, whichever occurs first.
2. WHEN an attempt ends THEN the daemon SHALL compute `hasDiff` by counting commits the agent made on top of the attempt's base commit — `git rev-list --count <base_sha>..HEAD` in the attempt's worktree — and treating `hasDiff = true` when that count is greater than `0`. The daemon SHALL NOT use `git status` (working-tree dirtiness) for this check: a correct agent commits its work, leaving a clean working tree, so a `git status`–based check would wrongly report no changes. `<base_sha>` is the commit the worktree was created from (recorded at attempt start; see Requirement 18).
3. The daemon SHALL classify every attempt end by evaluating the following **ordered, first-match list** and stopping at the first rule whose condition holds. The list covers every combination — including `exit = 0` with commits present and no self-report (rule 4), a `null` `exitCode` where the ACP `stopReason` fired before process exit (rules 3 and 7), and ACP never connecting (rule 7) — and no two rules overlap:

   1. IF the agent declared an outcome via the `report_outcome` tool with a valid `succeeded`\|`failed`\|`blocked` THEN the daemon SHALL use the declared outcome (agent-declared path): `succeeded` → `reason_code = NULL`; `failed` → `agent_reported_failure`; `blocked` → `agent_blocked`.
   2. ELSE IF the agent declared an outcome via `.agent-router/outcome.json` with a valid `succeeded`\|`failed`\|`blocked` THEN the daemon SHALL use the declared outcome (same reason-code mapping as rule 1).
   3. ELSE IF an ACP `stopReason` is present (regardless of exit code) and no outcome was declared THEN interpret the real ACP stop-reason enum (`end_turn | max_tokens | max_turn_requests | refusal | cancelled`):
      - `stopReason = 'end_turn'` → fall through to rule 4 (check for commits);
      - `stopReason = 'max_tokens'` OR `stopReason = 'max_turn_requests'` → `outcome = 'budget_exceeded'`, `reason_code = 'budget_exceeded'`, `failure_class = NULL`. (A budget overrun is recorded as the `budget_exceeded` outcome — the same outcome the budget enforcer of Requirement 17 produces — rather than a bare `failed`; this keeps the `outcome`→`reason_code` pairing closed and consistent with Requirement 6.8. The parent task still lands in `failed` via Requirement 3.4, so it remains retry-eligible exactly as a `failed` end would be.)
      - `stopReason = 'refusal'` → `outcome = 'failed'`, `reason_code = 'agent_reported_failure'`, `failure_class = NULL`;
      - `stopReason = 'cancelled'` with NO `termination_intent` set → `outcome = 'failed'`, `reason_code = 'agent_error'`, `failure_class = NULL` (HIGH-2: the agent SHALL NOT be able to self-cancel into a terminal `cancelled` task state; a legitimate cancel always arrives via an enforcer that sets `termination_intent` first — API cancel → `cancelled_by_api`, breaker cancel → `failed`/`cancelled_by_breaker` — which wins at the termination-intent check of Requirement 16.8 before this rule is reached);
      - any other `stopReason` value → `outcome = 'failed'`, `reason_code = 'agent_error'`, `failure_class = NULL`.
   4. ELSE IF `hasDiff` (the `git rev-list --count <base_sha>..HEAD` count is `> 0`, i.e. commits exist locally) THEN the daemon SHALL run the post-exit remote-ref check of Requirement 22.5 (`git ls-remote origin refs/heads/<worktree_branch>` in the worktree, where `<worktree_branch>` is the attempt's stored `worktree_branch` — `agent/<attempt_id>` for a fresh attempt or `agent/<original_attempt_id>` for a resume, HIGH-4) BEFORE removing the worktree and compare the returned remote SHA to the worktree `HEAD` (`git rev-parse HEAD`), HIGH-7: IF the remote branch is absent OR its SHA does NOT equal the local `HEAD` (the agent pushed only partial work, or an early push that later commits advanced past) → `outcome = 'failed'`, `reason_code = 'git_push_failed'`, `failure_class = 'infra'`, and the worktree SHALL be retained (Requirement 18.4); ELSE IF the remote branch is present AND its SHA equals the local `HEAD` (the full committed work landed) → `outcome = 'succeeded'`, `reason_code = NULL`, `failure_class = NULL`; IF the `git ls-remote` call itself fails (a network/transport error — non-zero exit and NO SHA returned) THEN the daemon SHALL set `remoteBranchExists = NULL` and classify the end as `outcome = 'failed'`, `reason_code = 'git_push_failed'`, `failure_class = 'infra'` (it SHALL NOT be classified `succeeded`), while NOT incrementing the repo's `consecutive_failures` counter for this particular case (Requirement 22.8 / 12.5), since a transient network error is not a repeatable agent/infra fault that should trip the breaker.
   5. ELSE IF `cleanEnd` AND there are no commits (`hasDiff = false`) AND no outcome was declared THEN `outcome = 'failed'`, `reason_code = 'no_changes'`, `failure_class = NULL`, where `cleanEnd = (stopReason === 'end_turn') OR (exitCode === 0)`.
   6. ELSE IF `exitCode !== NULL` AND `exitCode !== 0` AND no outcome was declared THEN `outcome = 'failed'`, `reason_code = 'agent_error'`, `failure_class = NULL`.
   7. ELSE (catch-all: `exitCode === NULL` AND `stopReason` is absent — the ACP adapter never connected and the process never exited cleanly) THEN `outcome = 'failed'`, `reason_code = 'agent_error'`, `failure_class = NULL`.

4. The agent SHALL be responsible for committing its changes, pushing the branch, and opening the pull request. The router SHALL NOT commit, push, or open the PR on the agent's behalf for attempt work.
5. WHEN an attempt ends `succeeded` THEN the daemon SHALL observe `pr_url` from the agent's `report_outcome` payload or from `.agent-router/outcome.json` and persist it into `artifacts.pr_url`; IF no `pr_url` is available THEN `artifacts.pr_url` SHALL be `NULL`.
6. A `succeeded` outcome SHALL set `reason_code = NULL` and `failure_class = NULL` (consistent with Requirement 6.8).
7. The daemon SHALL close the ACP connection and send `SIGTERM` to the agent process when: (a) budget limits are hit (Requirement 17), (b) `cancel` is called (Requirement 5.4), or (c) the `timed_out` enforcer fires (Requirement 17.1). The daemon SHALL wait up to 5 seconds for a clean process exit and THEN send `SIGKILL` if the process has not exited.
8. Each enforcer (the wall-clock/`timed_out` enforcer, the token/turn `budget_exceeded` enforcer, the API `cancel` path, AND the circuit-breaker cancel path of Requirement 12.9) SHALL atomically mark the attempt's in-memory **termination intent** BEFORE signaling the process (before closing the ACP connection or sending `SIGTERM`). The `resolveOutcome` function SHALL check this termination intent **first**; IF it is set THEN the daemon SHALL use the enforcer's outcome, reason code, and failure class regardless of what the agent subsequently reported via `report_outcome` / `outcome.json` or what the mechanical classification would produce. This prevents a race where the agent emits a late `report_outcome` (or the ACP returns a `stopReason`) between the enforcer's decision and the process exit.
9. The in-memory attempt state SHALL carry a `termination_intent: TerminationIntent | null` field, where `TerminationIntent = { outcome: AttemptOutcome, reasonCode: ReasonCode, failureClass: FailureClass | null }`. A bare outcome string is insufficient because the circuit-breaker cancel (Requirement 12.9) must carry `{ outcome: 'failed', reasonCode: 'cancelled_by_breaker', failureClass: 'infra' }`, which a single outcome value cannot express. The permitted intents are: `{ 'timed_out', 'timed_out', null }`, `{ 'budget_exceeded', 'budget_exceeded', null }`, `{ 'cancelled', 'cancelled_by_api', null }` (API cancel), and `{ 'failed', 'cancelled_by_breaker', 'infra' }` (breaker cancel). This field is **not persisted** to the `attempts` table; it exists only for the lifetime of the running attempt to arbitrate the attempt-end race (Requirement 15 conditional-UPDATE still guarantees the end is written exactly once).
10. The daemon SHALL provide a single `teardownAttempt(attemptId, endState: AttemptEndState, skipKill = false)` function through which **every** attempt-end path flows — normal `end_turn`, lease expiry, idle timeout, the `timed_out` enforcer, the `budget_exceeded` enforcer, the API `cancel`, the circuit-breaker cancel, and restart recovery — so that process termination, worktree cleanup, and event emission are specified in exactly one place.

    `AttemptEndState` (HIGH-1) is a superset of `TerminationIntent`: `{ outcome, reasonCode, failureClass, blocked?, artifacts?, usage? }`. The enforcer / cancel / breaker / lease paths pass only `{ outcome, reasonCode, failureClass }` (a `TerminationIntent`, assignable because `blocked`/`artifacts`/`usage` are optional); the **natural end path** (`resolveOutcome`) passes the full `endState` including the agent-reported `pr_url` inside `artifacts` (HIGH-5), together with `diff_stats`/`head_sha`/`transcript_ref` and `usage`. The conditional end-claim UPDATE (Step 0) SHALL persist **every field present on `endState`** — the `blocked` JSON (only when `outcome = 'blocked'`), the `artifacts` JSON (including `artifacts.pr_url`), and `usage` — into the `attempts` row and the `attempt.ended` event payload, so a natural end's `pr_url` and artifacts are recorded, while an enforcer end (which omits them) records them as `NULL`.

    **`teardownAttempt` is the single running→ended transition and NEVER inspects `termination_intent`.** `termination_intent` is consumed by the callers (Requirement 4.1a Rules 1 and 3 — the cancel/breaker path and the spawner's post-spawn re-check), not inside `teardownAttempt`. The function performs the following steps in order:

    - **Step 0 — Conditional end-claim.** Run `UPDATE attempts SET state = 'ended', outcome = ?, failure_class = ?, reason_code = ?, reason = ?, blocked = ?, artifacts = ?, usage = ?, agent_version = ?, model = ?, ended_at = ? WHERE id = ? AND state = 'running'` (Requirement 15), writing all `endState` fields. IF **0 rows** change THEN return immediately — the attempt was already ended by another concurrent path; no kill, no event, no worktree change. This is the ONLY place that transitions an attempt from `running` to `ended`. **The `artifacts` write SHALL MERGE `endState.artifacts` into the attempt's existing `artifacts` JSON rather than replacing it (HIGH-C):** read the current `attempts.artifacts` (defaulting to `{}` when NULL), shallow-merge `endState.artifacts` on top of it, and write back the merged object — `const existing = JSON.parse(attempt.artifacts ?? '{}'); const merged = { ...existing, ...endState.artifacts };`. This preserves the `branch`, `base_sha`, and `transcript_ref` recorded in `artifacts` at attempt start (Requirement 18.5) when an enforcer path (`timed_out`, `cancelled`, lease expiry) calls `teardownAttempt` with `artifacts: undefined`.
    - **Step 1 — Kill the process (skippable).** IF `skipKill = false` AND `attempts.pid IS NOT NULL` THEN close the ACP stdio connection, verify PID identity (Requirement 13.12), send `SIGTERM` to the process group (via the stored `pid`/`pgid`), wait up to 5 seconds, and send `SIGKILL` to the process group if still alive (Requirement 16.7). IF `skipKill = true` OR `pid IS NULL` (no process was ever spawned) THEN this step is skipped. `skipKill = true` is passed by exactly two kinds of caller, both cases where no agent process can meaningfully be killed: (1) **startup restart recovery** (Requirement 13.12), where the agent process is already dead after a reboot and the stored `process_start_time` can never match a recycled PID, so leaving the kill enabled would skip-and-warn on every attempt or risk signaling a recycled PID; and (2) **pre-session infra failures** (`spawn_failed`/`auth_failed`/`rate_limited`; Requirement 22.8a), where the fork/exec or the GitHub setup validation failed *before any agent process was ever created*. All other callers — including the lease checker and idle-timeout enforcer at setup-window expiry (Rule 2 of Requirement 4.1a / 4.5 / 17.6) and the setup-timeout hang path (Requirement 4.1c), where a spawned process may already be alive — pass `skipKill = false`; when such a call targets a still-pidless attempt, this step is skipped anyway by the `pid IS NULL` guard, but when the pid has in fact been recorded the kill steps run and reap the process.
    - **Step 2 — Worktree cleanup.** Remove the worktree with `git worktree remove --force` (the `--force` flag handles a **partially-created worktree** from a mid-setup `spawn_failed`, HIGH-3) per the Requirement 18 rules, EXCEPT the Requirement 18.4 retention cases (`reason_code = 'git_push_failed'`, or `outcome = 'interrupted'` with `allow_resume = true`).
    - **Step 3 — Emit `attempt.ended`.** Emit the `attempt.ended` event with the full `endState` payload, in the same SQLite transaction as the Step 0 UPDATE (Requirement 15.1).
    - **Step 4 — `onAttemptEnded`.** Call `onAttemptEnded(endState)` to update the circuit breaker (Requirement 12.5, honoring `endState.countsTowardBreaker`) and release the repo slot, and emit the task state transition.

    Steps 0, 3, and 4 are one SQLite transaction; Steps 1–2 are the process/filesystem side effects performed only when Step 0 claimed the end. The function is idempotent and race-safe by virtue of Step 0's conditional UPDATE. `teardownAttempt` does **not** check `attempts.pid` to decide whether to run — a caller that must not tear down a pidless attempt (a cancel/breaker during the setup window) makes that decision itself via Requirement 4.1a Rule 1 and does not call `teardownAttempt`.

### Requirement 17: Budget enforcement (timed_out and budget_exceeded)

**User Story:** As an operator, I want the router to enforce wall-clock and token/turn budgets, so that a runaway attempt is stopped and recorded with the right outcome.

#### Acceptance Criteria

1. WHEN an attempt's elapsed wall time (`usage.wall_ms`) exceeds `budget.max_wall_s × 1000` THEN the daemon SHALL set the full `termination_intent = { outcome: 'timed_out', reasonCode: 'timed_out', failureClass: null }` (a complete `TerminationIntent` triple per Requirement 16.8/16.9, NOT a bare outcome string), close the ACP connection, send `SIGTERM`, escalate to `SIGKILL` after a 5-second grace (Requirement 16.7), and end the attempt with `outcome = 'timed_out'`, `reason_code = 'timed_out'`, `failure_class = NULL`.
2. WHEN an attempt's token count exceeds `budget.max_tokens` OR its turn count exceeds `budget.max_turns` THEN the daemon SHALL set the full `termination_intent = { outcome: 'budget_exceeded', reasonCode: 'budget_exceeded', failureClass: null }` (a complete `TerminationIntent` triple per Requirement 16.8/16.9, NOT a bare outcome string), end the agent session via the ACP adapter (close connection, `SIGTERM`, 5-second grace, then `SIGKILL`; Requirement 16.7), and end the attempt with `outcome = 'budget_exceeded'`, `reason_code = 'budget_exceeded'`, `failure_class = NULL`.
3. The daemon SHALL evaluate budget limits on each `attempt.heartbeat` tick (and on relevant ACP activity for token/turn counts), using the configured budget on the task; limits that are absent SHALL be treated as unbounded.
4. WHEN a budget-enforced end occurs THEN the task SHALL transition to `failed` (Requirement 3.4) and the attempt SHALL remain eligible for retry via Requirement 5.
5. A budget-enforced end (`timed_out` or `budget_exceeded`) SHALL NOT increment the repo's `consecutive_failures` counter (Requirement 12.5).
6. WHEN an attempt is running AND `now() - last_activity_ts > idle_timeout_s` (configurable, default `900` seconds) THEN the daemon SHALL treat the agent as stuck. The idle-timeout enforcer is a Rule 2 caller of Requirement 4.1a: for an attempt still in the setup window (`pid IS NULL`) it applies Rule 2 — SKIP while `now() < started_at + setup_timeout_s × 1000`, else tear down with `skipKill = false` (the agent process may already be alive at window expiry; `teardownAttempt` internally skips its kill steps when `pid IS NULL`). For a running attempt (`pid IS NOT NULL`, the normal idle case) the daemon SHALL: (1) set the full `termination_intent = { outcome: 'timed_out', reasonCode: 'timed_out', failureClass: null }` (a complete `TerminationIntent` triple per Requirement 16.8/16.9), and (2) end the attempt by calling `teardownAttempt(attempt_id, { outcome: 'timed_out', reasonCode: 'timed_out', failureClass: null }, /* skipKill */ false)` (Requirement 16.10) — NOT `endAttemptWithEvent` directly. Routing the idle-timeout end through the single `teardownAttempt` path (HIGH-C, same slot-leak fix as HIGH-2) performs the ACP close + `SIGTERM` → 5-second grace → `SIGKILL` process kill (Requirement 16.7), removes the worktree, emits `attempt.ended` and the task-state transition, AND critically notifies `RepoScheduler.onAttemptEnded` so the repo slot is released and the queue drains; ending via `endAttemptWithEvent` directly would skip `onAttemptEnded`, leaking the slot. This **idle timeout** is distinct from the heartbeat lease expiry of Requirement 4.5: the lease detects a **daemon stall** (the daemon stopped refreshing the lease), whereas the idle timeout detects an **agent stall** — the agent is still connected but has produced no activity (`last_activity_ts` is the timestamp of the last ACP tool call or message). A `timed_out` idle end, like any `timed_out`, does NOT increment `consecutive_failures`.

### Requirement 18: Worktree lifecycle

**User Story:** As an operator, I want each attempt to run in an isolated git worktree that is reliably created and cleaned up, so that attempts never collide and stale state cannot be spoofed.

#### Acceptance Criteria

1. WHEN a **FRESH (non-resume) attempt** starts (`tasks.resume_session_id IS NULL`) THEN the daemon SHALL create a git worktree via `git worktree add /tmp/agent-runs/<attempt_id> -b <worktree_branch> <base_ref>`, where `<base_ref>` is the task's `base_ref` or the repo default branch when absent, and `<worktree_branch>` is the value stored in the attempt's `attempts.worktree_branch` column (set during `startAttemptWithEvent`, Requirement 4.1 / 18.5) — `agent/<attempt_id>` for a fresh attempt. The `-b` flag is REQUIRED precisely because the branch does not yet exist for a fresh attempt; the daemon SHALL NOT hardcode `agent/<attempt_id>` in the shell string, it SHALL interpolate the stored `worktree_branch` value. (Resume attempts are governed by Requirement 18.6, which does NOT run `git worktree add`.)
2. WHEN a FRESH attempt's worktree is created THEN the `-b <worktree_branch>` flag of Requirement 18.1 SHALL create and check out that new branch (`agent/<attempt_id>`) from `<base_ref>`, and the daemon SHALL record the resolved base commit SHA (`<base_sha>` = `git rev-parse HEAD` in the fresh worktree) on the attempt for later `hasDiff` computation (Requirement 16.2). This applies to fresh attempts only; a resume reuses the base SHA copied forward per Requirement 18.6.
3. IF a `.agent-router/outcome.json` file pre-exists in the worktree before the session starts THEN the daemon SHALL delete it, so a stale file from a previous run cannot spoof the outcome.
4. WHEN `attempt.ended` has been emitted (for both success and failure) THEN the daemon SHALL remove the attempt's worktree, EXCEPT in two cases where it SHALL retain the worktree:
   - WHEN the attempt ended `failed` with `reason_code = 'git_push_failed'` (commits exist locally but the remote branch is absent per Requirement 22.5) — the worktree is retained so a retry can re-push the already-committed work rather than redo it; and
   - WHEN `outcome = 'interrupted'` AND the task's `budget.allow_resume = true` (Requirement 13.6 / HIGH-7 resume path) — the worktree is retained so the resumed session continues in place.
   In all other cases the worktree SHALL be removed.
5. The worktree path, branch name, and resolved `<base_sha>` SHALL be recorded in `artifacts` (`branch`, `base_sha`) for the attempt. The branch name SHALL ALSO be stored in the dedicated `attempts.worktree_branch TEXT` column (HIGH-4) — `agent/<attempt_id>` for a fresh attempt, `agent/<original_attempt_id>` for a resume (Requirement 13.6) — so the preamble (Requirement 23.4) and the post-exit remote-ref push check (Requirement 22.5) both read the single authoritative branch value. For a fresh attempt `artifacts.branch` equals `worktree_branch`; for a resume both record the original branch. The absolute worktree path SHALL ALSO be stored in a dedicated `attempts.worktree_path TEXT` column (H2), set at attempt start to `/tmp/agent-runs/<attempt_id>`, so a resume (Requirement 18.6) can locate and reuse the retained worktree of the interrupted attempt without recomputing it.
6. WHEN a **RESUME attempt** starts (`tasks.resume_session_id IS NOT NULL`, the bounded `allow_resume = true` path of Requirement 13.6) THEN the daemon SHALL NOT run `git worktree add` (the branch already exists, so `git worktree add -b` would fail with a "branch already exists" error and the attempt would end `spawn_failed`). Instead the daemon SHALL reuse the retained worktree directory from the interrupted attempt — read from that interrupted attempt's `attempts.worktree_path` (retained per the Requirement 18.4 `interrupted` + `allow_resume` exception) — and SHALL copy `worktree_branch` (the original `agent/<original_attempt_id>`) and `artifacts.base_sha` forward from the interrupted attempt row into the new resume attempt row. The resume attempt's `attempts.worktree_path` SHALL equal the interrupted attempt's `worktree_path`. Because `base_sha` is copied forward (NOT re-derived as `HEAD`), the resume's `hasDiff` computation (`git rev-list --count <base_sha>..HEAD`) counts the pre-crash commits the interrupted attempt already made, so a resumed attempt that produced work before the crash is not misclassified as `no_changes`. The worktree-existence precondition of Requirement 13.6 (HIGH-5(d)) is checked against this `worktree_path`: IF the directory no longer exists the daemon SHALL fall back to `failed`/`interrupted` and SHALL NOT start the resume.

### Requirement 19: Circuit breaker persistence

**User Story:** As an operator, I want circuit-breaker state to survive a daemon restart, so that a paused repo stays paused across crashes.

#### Acceptance Criteria

1. The daemon SHALL persist per-repo circuit-breaker state (`consecutive_failures`, `circuit_breaker_state` ∈ `closed|open|half-open`, `paused_at`, `paused_until`) in a `repo_state` table (or equivalent columns on an existing repo/project table).
2. WHEN the daemon starts THEN it SHALL load the persisted circuit-breaker state so a repo that was paused before the restart remains paused.
3. WHEN the breaker opens or closes THEN the daemon SHALL write the `repo.paused` / `repo.resumed` event and the `repo_state` update in the same SQLite transaction.

### Requirement 20: ROADMAP importer specification

**User Story:** As a maintainer, I want the ROADMAP importer behavior fully specified, so that scans, write-back, and idempotency are deterministic.

#### Acceptance Criteria

1. The importer SHALL be triggered by a cron tick on a configurable interval.
2. The importer SHALL read `ROADMAP.md` from the repo's default branch via git.
3. The importer SHALL derive a task's `title` from the checklist item text with any annotation comment (`<!-- ar:<ULID> -->`) stripped.
4. The importer SHALL derive a task's `spec` from the full ROADMAP item text block.
5. WHEN a task reaches state `succeeded` THEN the importer SHALL update the item's checkbox to `[x]` and commit and push the change to the repo (a direct git commit by the router using the configured GitHub token).
6. The importer SHALL skip items already marked `[x]`, and `external_id` idempotency (Requirement 1.3) SHALL prevent duplicate task creation on re-scan.
7. Before scanning, the importer SHALL bring the roadmap branch up to date with `git pull --ff-only` so it reads the latest committed annotations and cannot re-annotate an item another instance already annotated.
8. `submitTask()` SHALL be called only AFTER the annotation commit has been **pushed successfully**. The importer SHALL handle push outcomes as follows:
   - IF the annotation `git push` is rejected as a stale-ref conflict (another writer advanced the branch; git exit code: non-ff rejection) THEN the importer SHALL: (1) discard the local annotation commit, (2) run `git pull --ff-only`, and (3) restart the scan from the beginning (re-reading the now-updated file). It SHALL NOT call `submitTask()` for the discarded annotation.
   - IF the default branch is **protected** (the push is rejected with a permission error) THEN the importer SHALL log a warning and **skip the annotation write-back**, deriving the task's `external_id` from a content hash of the item instead so idempotency still holds without writing to the repo.
   - Only on a successful annotation push does the importer call `submitTask()` using the pushed annotation id as `external_id`.

   The push-before-submit ordering means the pushed annotation id is the authoritative idempotency key: a second importer that pulls sees the annotation and derives the same `external_id`. **The SQLite `UNIQUE(external_id)` constraint does NOT by itself prevent duplicates from two concurrent importers that each minted a *different* ULID before either pushed** — two different ULIDs are two different `external_id` values and would create two tasks. Correctness therefore depends on the push-before-submit ordering (the stale-ref-conflict rejection forces the losing importer to re-pull and adopt the winner's annotation), not on the `UNIQUE` constraint; the constraint is only a backstop against the *same* `external_id` being submitted twice.

### Requirement 21: Additional read endpoints

**User Story:** As a UI, I want endpoints to list a task's attempts, list configured repos, and stream a transcript, so that I can render full history.

#### Acceptance Criteria

1. WHEN a client sends `GET /v1/tasks/:id/attempts` THEN the daemon SHALL return `200` with an array of all attempts for the task (ordered by `attempt_no`) and `"v": 1`; IF the task does not exist THEN it SHALL return `404` with `error.code = 'not_found'`.
2. WHEN a client sends `GET /v1/repos` THEN the daemon SHALL return `200` with `"v": 1` and a `repos` array in which each element has the canonical **flat** shape `{ repo: string, circuit_breaker_state: 'closed'|'open'|'half-open', consecutive_failures: number, paused_until: number|null, slots_total: number, slots_in_use: number }`. The single-repo endpoint `GET /v1/repos/:owner/:name/status` (Requirement 12.3) returns one such object. This flat shape is the single source of truth for repo status; design §6 `statusSnapshot` produces exactly this shape and the daemon SHALL NOT nest the breaker fields under a sub-object. (`paused_until` is serialized ISO-8601 per Requirement 2.7 when present; `null` when the repo is not paused.)
3. WHEN a client sends `GET /v1/attempts/:id/transcript` with `Accept: text/event-stream` THEN the daemon SHALL stream new transcript log lines as Server-Sent Events; WHEN the same endpoint is requested without that `Accept` header THEN the daemon SHALL return the full transcript as `text/plain`.

### Requirement 22: Infra-failure classification (`classifyPreSessionInfra`)

**User Story:** As an operator, I want a single, well-defined place where infrastructure failures are detected and assigned an infra reason code, so that the circuit breaker (Requirement 12) can actually open — today no code path produces the infra reason codes, so the breaker can never open.

#### Acceptance Criteria

1. The daemon SHALL define a function `classifyPreSessionInfra(sessionResult): PreSessionInfraReasonCode | null` that runs **after the agent session has exited and before the self-report / mechanical classification** (Requirement 16.3), where `PreSessionInfraReasonCode` is the closed set `{ spawn_failed, auth_failed, rate_limited, adapter_crash }`. This function detects ONLY the pre-session / adapter infra failures that occur before any agent self-report is possible; `git_push_failed` is NOT one of them — it is detected separately by the post-exit, post-self-report remote-ref check of Requirement 22.5 (step 5 of the merged order, Requirement 22.9). The full infra reason-code set that feeds the circuit breaker (Requirement 12.5) is therefore `{ spawn_failed, auth_failed, rate_limited, adapter_crash } ∪ { git_push_failed }`.
2. The function SHALL return `spawn_failed` WHEN the fork/exec of the agent CLI throws `ENOENT`, `EACCES`, or `EPERM`.
3. The function SHALL return `auth_failed` WHEN a GitHub API call made during session setup — specifically `GET /repos/:owner/:repo`, validated BEFORE the agent session starts — returns HTTP `401` or `403`, OR the agent's stderr tail matches an auth-related error pattern.
4. The function SHALL return `rate_limited` WHEN that same setup call (`GET /repos/:owner/:repo`) returns HTTP `429`.
5. The daemon SHALL detect `git_push_failed` as a **post-exit router check performed BEFORE worktree removal** (not by inspecting the agent's own push attempt, which the router cannot observe directly). The check SHALL run only after the agent process has exited AND `hasDiff = true` (commits exist locally): the daemon SHALL run `git ls-remote origin refs/heads/<worktree_branch>` in the attempt's worktree (where `<worktree_branch>` is the attempt's stored `worktree_branch` column — `agent/<attempt_id>` for a fresh attempt or `agent/<original_attempt_id>` for a resume, HIGH-4) and compare the returned remote SHA to the worktree `HEAD` (`git rev-parse HEAD`), HIGH-7. The check SHALL verify the FULL work landed, not merely that the ref exists:
   - IF the remote branch does NOT exist, OR it exists but its SHA does NOT equal the local `HEAD` (the agent pushed early and then made more commits, so only partial work is on the remote) THEN the agent's push did not fully land → `remoteBranchExists` is treated as "not matching" → `outcome = 'failed'`, `reason_code = 'git_push_failed'`, `failure_class = 'infra'`, and the daemon SHALL NOT remove the worktree (it SHALL retain it for retry; Requirement 18.4 exception). This end DOES increment `consecutive_failures` (Requirement 22.8).
   - IF the remote branch exists AND its SHA equals the local `HEAD` THEN the push succeeded and the daemon SHALL proceed to the `succeeded` classification (Requirement 16.3 rule 4).
   - IF the `git ls-remote` call itself FAILS (network/transport error — non-zero exit and no SHA returned) THEN the daemon SHALL set `remoteBranchExists = NULL` and SHALL NOT classify the end as `succeeded`; it SHALL classify it `failed`/`git_push_failed`/`infra` (retaining the worktree) but SHALL NOT increment `consecutive_failures` for this case (Requirement 22.8 / 12.5), because a transient `ls-remote` network failure is not a repeatable fault that should open the breaker.

   This replaces any notion of the router running `git push` itself (Requirement 16.4 forbids the router from pushing); the router only *verifies* that the agent's push landed in full on the remote. `SessionResult.remoteBranchExists` is therefore a three-valued `boolean | null`: `true` = ref present AND SHA matches `HEAD`; `false` = ref absent or SHA mismatch; `null` = `ls-remote` failed.
6. The function SHALL return `adapter_crash` WHEN the ACP stdio connection closes with a non-zero exit BEFORE the first ACP event is received (the adapter never came up).
7. The function SHALL return `null` WHEN none of the above infra conditions is detected, allowing the attempt end to fall through to the mechanical classification of Requirement 16.3.
7a. For a **pre-attempt failure** (a `spawn_failed` / `auth_failed` / `rate_limited` detected before any `attempts` row exists), the daemon SHALL create the attempt row immediately before the setup phase so that the failure has a row to record its outcome against. Concretely: the scheduler creates the `attempts` row (and emits `attempt.started`) first, then runs the GitHub setup validation and the agent spawn; a setup/spawn failure then ends that already-created attempt by routing through `teardownAttempt(attempt_id, termination_intent ?? { outcome: 'failed', reasonCode: <code>, failureClass: 'infra' }, /* skipKill */ true)` — passing the higher-priority of (`termination_intent`, the infra-failure endState) with `termination_intent` taking precedence (HIGH-B / Requirement 22.8a) — NOT by calling `endAttemptWithEvent` directly — so a Case A cancel that landed during the setup window ends the attempt as `cancelled` rather than `failed`, while the circuit-breaker counter is incremented and the slot released via `onAttemptEnded` for a genuine infra failure. This guarantees every infra failure — including those that occur before the agent runs — is observable as an `attempt.ended` event on a real attempt row.
8. WHEN `classifyPreSessionInfra` returns a non-null `PreSessionInfraReasonCode`, OR the post-exit remote-ref check of Requirement 22.5 detects `git_push_failed` because the remote branch is absent or its SHA mismatches `HEAD` (`remoteBranchExists = false`), THEN the daemon SHALL end the attempt with `outcome = 'failed'`, that `reason_code`, and `failure_class = 'infra'`, and this end SHALL increment the repo's `consecutive_failures` counter per Requirement 12.5 (feeding the circuit breaker). EXCEPTION (HIGH-7): WHEN the `git ls-remote` call itself failed (`remoteBranchExists = null`, a transient network/transport error) THEN the attempt SHALL still end `failed`/`git_push_failed`/`infra`, but the daemon SHALL NOT increment `consecutive_failures` for that end — a transient `ls-remote` failure is not a repeatable fault that should trip the breaker.
8a. **Pre-session infra ends MUST route through `teardownAttempt`, not `endAttemptWithEvent` directly (HIGH-2), and MUST honor a pending `termination_intent` (HIGH-B).** The three pre-session infra failures (`spawn_failed`, `auth_failed`, `rate_limited`) occur before the agent is running and before any self-report is possible. Because a pre-session infra failure can race a Rule 1 cancel — an API or circuit-breaker cancel (Requirement 4.1a Rule 1 / 5.4 / 12.9) may already have set the attempt's in-memory `termination_intent` during the setup window — the spawner SHALL check `termination_intent` BEFORE constructing the endState and SHALL pass the **higher-priority of (`termination_intent`, the infra-failure endState)** to `teardownAttempt`, with `termination_intent` taking precedence: `teardownAttempt(attempt_id, termination_intent ?? { outcome: 'failed', reasonCode: <code>, failureClass: 'infra' }, /* skipKill */ true)` (Requirement 16.10). The nullish coalescing ensures a pending cancellation intent takes precedence over the infra failure outcome — a cancel landing during the setup window ends the attempt `cancelled`/`cancelled_by_api` (or `failed`/`cancelled_by_breaker` for a breaker cancel) rather than `failed`/retry-eligible — and only when no intent is pending (`termination_intent` is `null`) does the attempt end with the infra failure. It SHALL NOT call `endAttemptWithEvent` directly for these ends. Using `skipKill = true` is correct because the spawn failed before any process (or any live process) existed to kill, so the SIGTERM/SIGKILL/ACP-close steps are skipped; the `teardownAttempt` path still (a) runs the conditional end-claim UPDATE and emits `attempt.ended` + the task-state transition, (b) runs `git worktree remove --force` to clean up any partially-created worktree (Requirement 4.1b), and — critically — (c) calls `RepoScheduler.onAttemptEnded(endState)` so the circuit-breaker counter is incremented (Requirement 12.5) and the repo slot is released. Routing these ends directly through `endAttemptWithEvent` would skip `onAttemptEnded`, so the breaker could never open on repeated setup failures and the slot would leak — which is the defect this requirement closes.
9. The daemon SHALL evaluate the merged classification in this fixed order (HIGH-2), stopping at the first producing step:
   1. **spawn_failed / adapter_crash** — pre-start infra failures where no agent self-report was possible (the agent never ran or the adapter never connected).
   2. **auth_failed / rate_limited** — setup-phase infra failures detected before the agent session starts (the GitHub `GET /repos/:owner/:repo` validation of Requirement 22.3/22.4).
   3. **Self-report** via `report_outcome` or `.agent-router/outcome.json` (Requirement 16.3 rules 1–2).
   4. **ACP `stopReason`** (Requirement 16.3 rule 3).
   5. **git_push_failed** post-exit remote-ref check (Requirement 22.5 / Requirement 16.3 rule 4).
   6. **`hasDiff` + `cleanEnd` checks** (Requirement 16.3 rules 4–7).

   Steps 1–2 (setup failures) therefore **override** a self-report — they occur before any self-report is possible — while a self-report (step 3) **overrides** the mechanical steps 4–6. The `termination_intent` of Requirement 16.8 is checked before all of these and wins over every step. This replaces the earlier contradictory ordering where a single `classifyInfraFailure` (including `git_push_failed`) ran unconditionally after the agent exited (which would have let a late git-push or adapter check override a genuine self-report); `classifyPreSessionInfra` now produces only the pre-session / adapter codes consulted before the self-report, and `git_push_failed` is a separate step-5 check consulted after it.

### Requirement 23: Agent prompt preamble

**User Story:** As the daemon, I want every agent session to be told, in its initial prompt, how to report its outcome, so that the `report_outcome` channel (Requirement 7) is actually used instead of relying on mechanical fallback.

#### Acceptance Criteria

1. The daemon SHALL prepend a standard preamble to the initial prompt of **every** agent session before the task's `spec` text.
2. The preamble SHALL state that a `report_outcome` tool exists and SHALL enumerate its three valid `outcome` values: `succeeded`, `failed`, and `blocked`.
3. The preamble SHALL state that writing a `.agent-router/outcome.json` file in the worktree root is an accepted alternative to calling the tool, and SHALL describe its schema (`{ outcome, reason_code?, reason?, blocked?, pr_url? }`) with the same three allowed `outcome` values. The preamble SHALL tell the agent to include `pr_url` (in either channel) if it opened a pull request (HIGH-6).
4. The preamble SHALL instruct the agent that it MUST report its outcome through one of these two channels before the session ends, and that committing its work, pushing the branch, and opening the PR are the agent's responsibility (Requirement 16.4). The preamble SHALL state the **exact push command** the agent must use — `git push origin <branch_name>` with the attempt's real branch name interpolated (HIGH-7/HIGH-4) — so the agent pushes to the branch the router's post-exit remote-ref check inspects (Requirement 22.5) and cannot trigger a false `git_push_failed` by pushing to the wrong branch.

    **The branch name passed to the preamble SHALL be the attempt's actual push branch, NOT always `agent/<attempt_id>` (HIGH-4):**
    - For a **fresh (non-resume) attempt**, `branch_name = 'agent/<attempt_id>'`.
    - For a **resume attempt** (`allow_resume = true`, Requirement 13.6), `branch_name = 'agent/<original_attempt_id>'`, where `original_attempt_id` is the id of the first attempt for this task that used this session — the branch the resumed session already pushed to. Passing the NEW attempt id here would tell the agent to push to `agent/<new_attempt_id>` while the router's remote-ref check (Requirement 22.5) inspects the ORIGINAL branch, producing a false `git_push_failed`.

    The daemon SHALL store this branch name on the attempt row in a new column `attempts.worktree_branch TEXT` at attempt start, and SHALL pass that stored value both to `buildPromptPreamble` and to the post-exit `git ls-remote origin refs/heads/<worktree_branch>` push check (Requirement 22.5), so the agent and the router always agree on the branch. The daemon SHALL make the attempt id and `worktree_branch` available to `buildPromptPreamble` (Requirement 23.6).
5. The preamble SHALL NOT alter the task's `spec`; it is prepended as framing and the `spec` is preserved verbatim (and `prompt_hash` continues to be computed over the `spec` alone, Requirement 4.1).
6. The preamble text SHALL be a pure, independently testable function `buildPromptPreamble(task, attemptId, branchName)` of the task (agent kind, worktree path), the attempt id, and the explicit `branchName` (so it can embed the exact `git push origin <branchName>` command, HIGH-7/HIGH-4 — `agent/<attempt_id>` for a fresh attempt or `agent/<original_attempt_id>` for a resume) so its content can be unit-tested.
